# 모아 고객센터

100개 인텐트, 슬롯 수집, 대화 상태 추적(DST)을 갖춘 한국어 고객센터 챗봇입니다. 브라우저에서 대화와 현재 슬롯, 확인 대기, 중단한 문의를 함께 볼 수 있습니다.

분류에는 실행 중인 vllm-verifier의 `/v1/systemone` API를 사용합니다. Kai와 DiffusionGemma 모두 같은 API로 연결합니다. 대화 상태는 모델 밖에서 관리하므로 엔진을 바꿔도 슬롯 수집과 확인 절차는 같습니다.

## 실행

저장소 루트에서 실행합니다. Python 환경과 모델 설치는 [프로젝트 README](../../README.md)를 참고하세요.

터미널 하나에서 Kai 엔진을 실행합니다.

```sh
.venv-decision/bin/vllm-verifier --runtime decision --port 18080
```

다른 터미널에서 챗봇을 실행합니다.

```sh
.venv/bin/python -m examples.customer_service.app --port 18090
```

[http://127.0.0.1:18090](http://127.0.0.1:18090)을 엽니다. 서버는 로컬 호스트에만 바인딩합니다.

DiffusionGemma를 사용하려면 Kai를 종료하고 같은 포트에 MLX 엔진을 실행하세요. 두 모델을 동시에 올리면 메모리가 부족할 수 있습니다.

```sh
VERIFIER_MAX_CONCURRENCY=1 VERIFIER_MAX_OUTPUT_TOKENS=256 \
VERIFIER_MLX_CANVAS_TOKENS=64 \
.venv/bin/vllm-verifier --runtime mlx --port 18080
```

외부 엔진은 `--engine-url http://host:port`로 지정합니다. 인증이 필요하면 챗봇 프로세스에 `VERIFIER_API_KEY`를 설정하세요.

## 대화 예시

- “내 상품 언제 도착해?” → “ORD-1001” → “그 주문 현재 어디야?”
- “주문 수량 변경해줘” → “ORD-1002” → “2개” → “아니 3개” → “네”
- “반품하고 싶어” → “ORD-1001” → “상담사 연결해줘” → “채팅” → “네” → “이어서”
- “상품 검색” → “이어폰” → “에어버즈” → “그 상품 재고 알려줘”

필요한 정보를 순서대로 물으며, 변경 요청은 확인 후 처리합니다. “취소”는 현재 문의를 취소하고, “이어서”는 중단한 문의를 재개합니다. 분류가 모호하면 후보를 보여줍니다. 왼쪽 인텐트 목록을 클릭하면 모델 분류를 거치지 않고 선택한 업무를 시작합니다.

## 데이터와 동작 범위

모든 주문, 고객, 상품, 이벤트는 고정된 샘플입니다. 날짜도 실제 오늘 날짜와 무관합니다. 변경은 세션 메모리에만 반영되며 결제, 배송, 상담사 시스템에 전송되지 않습니다.

세션은 쿠키로 구분하며 한 시간 후 만료됩니다. 서버 재시작과 새 대화는 상태를 초기화합니다. 운영용 인증, 영구 저장, 실제 고객 데이터 접근은 포함하지 않습니다.

인텐트는 10개 분야에 각각 10개씩 있습니다. 모델은 분야와 세부 인텐트를 두 번에 나누어 분류합니다. 슬롯은 주문 번호, 샘플 상품명, 날짜 등 정해진 형식과 사전으로 추출합니다. 임의의 상품이나 복잡한 자연어 날짜를 이해하는 범용 슬롯 모델은 아닙니다. 한 번에 하나의 업무를 처리하며 업무 전환 시 기존 프레임을 보관합니다.

## 구조

- `catalog.json`: 100개 인텐트, 필수 슬롯, 실행 핸들러, 확인 여부
- `classifier.py`: 모델과 독립적인 System One 분류 클라이언트
- `dialogue.py`: 슬롯 수집, 수정, 확인, 중단과 재개
- `slots.py`: 슬롯 추출과 입력 검증
- `actions.py`, `fixtures.json`, `faqs.json`: 샘플 업무 처리와 데이터
- `app.py`, `static/`: 세션 API와 브라우저 화면

이 디렉터리는 설치 배포물의 엔진 소스와 분리되어 있습니다. 엔진 패키지를 설치해도 고객센터 데모는 포함되지 않습니다.

## 검증

```sh
.venv/bin/pytest tests/test_customer_service.py -q
.venv/bin/python -m examples.customer_service.evaluate \
  --output examples/customer_service/results/local.json
```

단위 테스트는 명시적인 테스트 대역을 사용합니다. 평가 명령은 실제 실행 중인 모델에 100개 카탈로그 예문을 전송합니다. 결과에는 오분류와 확인 요청을 그대로 기록합니다. 카탈로그 예문 평가는 별도의 실제 고객 대화 데이터에 대한 정확도나 멀티턴 성공률을 의미하지 않습니다.

### Kai 측정 결과

Apple M5 / 24GB에서 초기 분류 정책으로 카탈로그 예문 100개를 순서대로 실행한 결과입니다.
자동 분류 정답 27개, 확인 요청 62개, 오분류 11개였으며 요청당 중앙 지연은 약 50ms였습니다.
지연에는 HTTP와 분야·세부 인텐트 분류가 포함되며 별도의 워밍업은 하지 않았습니다.
현재 한국어 100개 업무의 자동 분류 품질은 부족합니다. 업무 목록에서 직접 선택하거나
확인 후보를 선택할 수 있지만, 이를 모델의 정확도 향상으로 계산하지 않습니다.
원본은 [Kai 평가 결과](results/kai-catalog.json)에 있습니다.

### DiffusionGemma 확인 범위

동일 API와 두 모델의 응답 형식을 처리하는 계약 테스트는 통과했습니다.
2026-09-24 실모델 대화 검증에서는 첫 두 요청이 각각 90초 제한을 초과했고,
후속 두 요청도 서버 오류로 종료되었습니다. 따라서 이 데모의 DiffusionGemma
멀티턴 성공은 아직 검증되지 않았습니다. [실행 결과](results/gemma-multiturn.json)를
참고하세요. 이전의 짧은 질문 벤치마크를 이 100개 인텐트 작업의 성능으로 해석하면 안 됩니다.

실제 Kai HTTP 서버에서 배송 문의 → 주문번호 입력 → 수량 변경 문의 → 새 주문번호 →
수량 입력 → 수량 정정 → 최종 확인의 7턴 시나리오도 통과했습니다.
[대화 원본](results/kai-multiturn.json)에 각 턴의 상태와 모델 응답이 있습니다.
독립적인 새 문의에는 이전 업무 문맥을 보내지 않고, “그 주문” 같은 명시적 참조에만
문맥을 전달합니다. 이 한 시나리오의 통과가 모든 멀티턴 조합의 성공을 보장하지는 않습니다.

### 문의 전환

주문번호나 사유를 기다리는 중에도 “쿠폰 있어?”, “결제 수단은?”처럼 새 질문을 할 수 있습니다.
기존 문의는 중단 목록에 보관하며 “이어서”로 돌아갑니다. 새 질문의 분류가 불확실하면
기존 슬롯을 계속 묻지 않고 새 문의의 후보를 제시합니다. 사유처럼 질문 형태인 값을
입력하려면 “사유: …”처럼 필드명을 붙여 의도를 명확히 할 수 있습니다.
질문 감지는 한국어 규칙을 사용하므로 모든 표현을 완벽하게 구분하지는 않습니다.

분야와 세부 인텐트 모두에 확인 정책을 적용한 재평가에서는 100개 중
자동 정답 24개, 확인 요청 71개,
오분류 5개였습니다.
[재평가 원본](results/kai-catalog-interruptions.json)을 참고하세요.
이는 모델 재학습이 아니라 불확실한 자동 처리를 줄이는 정책 변경입니다.
